# Supported SQL and known limitations

## SQLite supported surface

The SQLite engine accepts one SQLite `SELECT` query per input, including ordinary CTEs,
joins, filters, grouping, aggregates, window expressions, compound queries,
`DISTINCT`, `ORDER BY`, and `LIMIT` when SQLite and `sqlglot` can parse and execute
them consistently.

The source database is never opened for writing. Queries run against in-memory
copies with parser validation, `PRAGMA query_only`, an SQLite authorizer, a
progress-handler deadline, and a configurable result-row cap.

Search uses the core's generic mutation families on the database's entity model. Tables
become collections, columns fields and foreign keys references; the families that matter for SQL
are boundary (harvested literals and their neighbors, as a copy of a row with the change),
missing (a copy of a row with a NULL), duplicate, empty (a parent with no children), dangling and
edge values (zero, negative, huge, empty or non-ASCII values drawn with Hypothesis). Two
mutations are composed when one is not enough (a row in a year no row has, with a NULL amount).
Search is bounded and deterministic for a fixed database, configuration, seed, package version,
Python version, and SQLite version. The families were named `boundary`, `null`, `duplicate`,
`join`, `filtering` and `aggregation` before 0.4.

## Explicitly unsupported

- More than one SQL statement, or empty SQL.
- DDL, DML, `PRAGMA`, `ATTACH`, `DETACH`, transactions, and extension loading.
- `VALUES` as the top-level statement.
- Queries that time out, exceed the result-row cap, or cannot be compared under
  the requested column policy.
- PostgreSQL DDL passed with `--engine sqlite` (give SQLite DDL, or an empty SQLite file,
  or use `--engine postgres`).
- Other SQL engines and dialects in the SQLite commands.

## Known limitations

- Search is heuristic, not a proof of equivalence or exhaustive state exploration.
- Query harvesting is lightweight and does not perform structural AST diffing.
- Window expressions execute natively, but there is no window-specific mutation
  family. Agreement for a window query is limited to the states actually tested.
- Complex `CHECK` expressions, regular expressions, trigger-dependent invariants,
  virtual tables, views, and cyclic generation dependencies may be skipped or
  reported as inconclusive.
- `AUTO` ordering treats a top-level `ORDER BY` on the reference query as ordered.
  Candidate-only ordering is ignored. Ties without a complete deterministic key may
  still have engine-dependent order.
- SQLite collation behavior is delegated to SQLite. Result comparison does not
  independently reproduce custom collation semantics.
- Trusted validator callbacks execute caller-provided Python and must not be loaded
  from untrusted files.
- Replay applies a 30-second execution deadline and 10,000-row result cap to each
  recorded query. Replays are intended for `isitright`-generated reports and fixtures;
  they are not a general sandbox for arbitrary SQLite programs.
- Reproductions retain table DDL and standalone unique indexes. Other performance-
  only indexes and triggers are intentionally omitted.
- Timing fields vary across runs. Other report fields and reproduction scripts are
  deterministic under the fixed-environment conditions above.

`NOT_FOUND_WITHIN_BUDGET` means only that no disagreement was observed in the
states actually tested. It is never a claim that the queries are equivalent.

## SQLite with an empty database

A SQLite file whose tables are all empty is treated as schema-only. Starting states
are synthesized with the generator shared with the PostgreSQL path, which supports
single-column integer, text and UUID keys; `INTEGER`/`INT`/`SMALLINT`/`BIGINT`,
`TEXT`, `VARCHAR(n)`/`CHAR(n)`, `REAL`/`DOUBLE`, `NUMERIC`/`DECIMAL(p,s)`, `BOOLEAN`,
`DATE`, and `TIMESTAMP` columns; and simple foreign keys. SQLite column defaults,
simple `CHECK` forms (`col IN (...)` and `col >= number`) and supplied JSON Schema
values guide the generated rows, and candidates are still validated by SQLite and the
domain constraints. Other schemas fall back to a simpler built-in synthesis. A
database with any rows is perturbed from its own rows.

`--engine sqlite` takes `--database` (a file) or `--schema` (SQLite DDL); `--engine postgres` and
`--engine duckdb` take `--schema` (PostgreSQL DDL).

## PostgreSQL support

`isitright sql check --engine postgres` and `isitright sql suite --engine postgres` accept unqualified tables
with a single-column `SMALLINT`, `INTEGER`, `BIGINT`, `TEXT`, `VARCHAR`, or
`UUID` primary key. Primary and simple foreign keys can be inline or table-level;
foreign-key columns must match the referenced primary-key type. Single-column
`UNIQUE`, literal defaults, and `GENERATED BY DEFAULT AS IDENTITY` are supported.
Columns may use those key types plus `NUMERIC`/`DECIMAL`, `REAL`,
`DOUBLE PRECISION`, `BOOLEAN`,
`DATE`, `TIMESTAMP`, and `TIMESTAMPTZ`. Search uses a small set of generated values,
not a comprehensive type-specific search.

Read-only, non-recursive CTEs, subqueries including correlated `EXISTS`, `IN`,
`CASE`, `HAVING`, `UNION`/`INTERSECT`/`EXCEPT`, selected window functions, and
casts to supported built-in types are accepted alongside the previously supported
SELECTs, filters, arithmetic, aggregates, ordering, and INNER/LEFT joins. Queries
and nested CTEs must contain only the allowlisted read-only syntax. Recursive
CTEs, data-modifying statements, user-defined functions, ambiguous references,
and constructs outside the allowlist are rejected.

`CHECK` constraints (column or table level) are accepted on PostgreSQL and DuckDB: the engine
enforces them, and the simple forms (`col IN (...)`, `col >= number`) also guide generation, as on
SQLite. A generated state a CHECK rejects is counted under `search.rejected`.

Still unsupported, with what the 0.5 measurement found (the PostgreSQL tests, the examples and the
cross-engine tests were run with every `SqlInputError` counted): composite primary keys (one test
asserts they are rejected; no example or test needs them), composite or cyclic foreign keys,
foreign-key actions, nonliteral defaults, unsupported type parameters and
`GENERATED ALWAYS AS IDENTITY`. Nothing in the existing tests or examples depends on composite
keys, so they were not added; a suite that needs them is the evidence to add them. DuckDB may
reject or behave differently on some otherwise supported PostgreSQL features, such as identity
columns; its findings remain explicitly emulated. This subset is not a claim of complete
PostgreSQL compatibility.

For parameterized `VARCHAR(n)`, the supported length is 1–10,000. For
`NUMERIC(p,s)`, precision is 1–1,000 and scale is 0–precision; PostgreSQL's
additional scale forms and other type parameters are not supported.

A schema-only run starts from one generated row per table (references matched), evaluates it,
then applies the generic families to depth two: boundary values around harvested literals, NULL
copies, duplicates, a parent without children, repeated children and nullable foreign keys. These
are bounded heuristics, not exhaustive combinations. Supplied JSON Schema domain constraints
validate normalized states, and row minimization rechecks them. No real PostgreSQL
database or seed data is required. Native mode runs the original queries on a
temporary local PostgreSQL server; `--engine duckdb` translates and executes them on
DuckDB and reports `EMULATED`. DuckDB schema validation is
not a native PostgreSQL validity check. Run `isitright sql replay` to reproduce
recorded outputs on the report's engine.

## Emulation and native verification

DuckDB is a candidate generator, not evidence. When the PostgreSQL extra is installed, every
state on which DuckDB reports a divergence is re-executed on a disposable PostgreSQL instance
(`--verify-native`, on by default; `--no-verify-native` turns it off):

- the results differ there too: the finding is `COUNTEREXAMPLE_FOUND`, `found_on: EMULATED`,
  `verified_on: NATIVE_ISOLATED`, with the native outputs under `divergence.native_results`. A
  verified finding may fail CI under `--fail-on`;
- the results agree there: an **emulation artifact**. It does not count as a counterexample, is
  counted under `search.rejected.emulation_artifact` and listed in
  `extensions.sql.emulation_artifacts`, and the case reports `native_verification:
  ARTIFACTS_EXCLUDED`;
- PostgreSQL is not available or the re-execution fails: the finding stays emulated and
  `NOT_VERIFIED` with the reason, and never fails CI.

Minimization keeps the native disagreement, so a minimized world is verified too.

**Integer division.** PostgreSQL divides two integers with truncation (`5 / 2` is 2); DuckDB's `/`
gives 2.5. The translation rewrites every `/` whose operands are both integers (by declared column
types and literals) to DuckDB's truncating `//`, guarded so a zero divisor is an error as in
PostgreSQL. A division whose types cannot be read is left as written and counted under
`extensions.sql.integer_division.uncertain`. Not translated: `numeric / integer` (exact in
PostgreSQL), and floating-point division by zero (an infinity in DuckDB, reported inconclusive).
